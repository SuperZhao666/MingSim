# 历史内容与证据生产规范

## 1. 为什么这也是技术设计

历史游戏最危险的两种错误：

- 把一段未经核对的聊天结论写成硬规则；
- 为了“真实”堆很多数字，却不知道数字适用于哪一年、哪一地、哪种口径。

结果会同时伤害玩法、代码和可信度。因此人物、机构、地图、财政和军队数据必须经过一条可追踪的内容生产线。

## 2. 四层证据标签

| 标签 | 意思 | 示例写法 | 能否直接写入游戏 |
| --- | --- | --- | --- |
| `FACT` 史料事实 | 来源直接支持，适用范围明确 | 某人在某日担任某职 | 可写初始事实，仍需版本/来源 |
| `INTERPRETATION` 机制解释 | 多项事实支持的因果理解 | 某制度常造成多机构协调 | 可作规则假设，必须标推导 |
| `DESIGN` 游戏化设计 | 为可玩性作的简化 | 将复杂文书归为 4 种路径 | 可实现，要经试玩而非伪称史实 |
| `OPEN` 未决假设 | 证据不足或冲突 | 某路线当月每日确切运力 | 不写死；研究、范围化或配置占位 |

任何“高置信”都必须来自证据记录，不是作者在正文里自己加一个标签。

## 3. Source Ledger（来源账本）

每条要进入生产内容的重要断言建一条记录：

```yaml
claim_id: hist-1629-ningyuan-001
claim: "待核对的具体、单一断言"
status: fact | interpretation | design | open
scope:
  time: "适用年代/日期"
  place: "适用地区"
  people: ["适用人物/群体"]
sources:
  - source_id: src-001
    type: primary | scholarly_secondary | reference | other
    title: "题名"
    author: "作者/机构"
    publication: "出版/档案信息"
    date: "出版或形成日期"
    locator: "卷、页、条目、稳定段落"
    url: "若有稳定链接"
    accessed_at: "查阅日期"
    supports: direct | partial | contradicts | context_only
evidence_summary: "用自己的话概括来源支持什么"
conflicts: ["相反证据或口径差异"]
confidence: high | medium | low
game_use: "将进入哪个人物/机构/规则/场景字段"
simplification: "做了什么游戏化简化"
reviewed_by: "审核人"
reviewed_at: "审核日期"
```

一条记录只处理一个可以判断真假的断言，不把“晚明财政很复杂”作为来源项。

## 4. 来源优先级

优先顺序不是绝对，但默认：

1. 可核对的一手档案、奏疏、实录、地方志原文及可靠影印/整理；
2. 同行评审论文、学术专著、权威数据库；
3. 可靠工具书、博物馆/档案馆/大学专题资料；
4. 有明确引用链的高质量二手说明；
5. 百科、论坛、视频、聊天研究只作为找线索入口。

原始策划中的 `citeturn...` 标记无法供团队直接打开核对，不能进入正式 Source Ledger；必须重新找到原页面/论文/书目和准确定位。

## 5. 从史料到规则的转换

```mermaid
flowchart LR
    Question["纵切提出具体问题"] --> Evidence["搜集并登记证据"]
    Evidence --> Claim["形成范围明确的断言"]
    Claim --> Mechanism["提出最小因果机制"]
    Mechanism --> Prototype["可配置规则原型"]
    Prototype --> Test["史实场景测试 + 玩法测试"]
    Test --> Review{"既可信又好玩吗？"}
    Review -->|"否"| Claim
    Review -->|"是"| Content["生产内容与发布说明"]
```

示例：

```text
史料事实：某批粮在某条路线曾经历特定损耗
≠ 所有年代、所有路线固定损耗 18%

机制解释：路线、天气、装卸、治安会造成损耗
→ 游戏规则：损耗由这些可观察因素计算
→ 场景数据：1629 某路线给出有来源的基线范围
```

## 6. 人物档案模板

```text
PersonId：稳定内容 ID
姓名/字/号/异名：
出生/死亡：证据与不确定范围
1629 当前身份和职位：
家庭与重要关系：每条关系来源
教育/仕途/军事经历：时间轴
财产、地方和组织联系：
已知言论与行为：原始语境
可推断能力：证据与置信度
可推断目标/人格：只写“设计推导”，不用现代标签冒充诊断
未知和冲突：
游戏化字段映射：
禁止推断：当前资料无法支持的内容
```

一次行为不能直接永久映射成“忠诚=20”“贪婪=90”。性格字段要表达概率倾向，并允许经历改变。

## 7. 机构与制度档案模板

```text
Institution/Office ID：
适用时期：
法定职责：
实际惯例：
上级/下级/并行机构：
辖区：
正式命令与文书渠道：
预算/人员/档案能力：
已知例外和时期变化：
Capability 映射：
Scope/Limit 映射：
来源：
游戏化简化：
```

要区分“法定能做什么”和“现实中经常做什么”。这正是机构能力与人物执行差异的玩法来源。

## 8. 地图、路线和数量数据

### 地图/路线

记录：

- 数据提供方和许可证；
- 数据版本/下载日期；
- 坐标系和处理脚本；
- 原始文件哈希；
- 做了哪些裁剪、简化和人工修正；
- 历史边界与现代底图之间的差异；
- 游戏拓扑与视觉几何怎样对应。

### 数量

每个历史数值至少附：

```text
单位
币制/重量/口径
时间
地区
名义值还是实得值
原始/换算值
换算公式与不确定范围
```

不要把“纸面兵额”“在营人数”“可战人数”放进同一个 `troop_count`。

## 9. 冲突证据处理

遇到来源冲突：

1. 不偷偷选择最符合玩法的一条；
2. 检查年代、地区、文种、统计口径和作者立场；
3. Ledger 同时记录支持与反对来源；
4. 能确定范围时用区间/分布；
5. 无法确定时标 `OPEN`；
6. 若玩法必须有值，使用明确的 `DESIGN` 默认值并可配置；
7. UI 需要时把不确定性变成情报差，而不是把后台数据也随机胡写。

## 10. 内容目录建议

等 1629 迁移正式批准后：

```text
content/ming_1629/
├─ manifest.json
├─ source-ledger/
│  ├─ claims.jsonl
│  └─ sources.jsonl
├─ characters/
├─ institutions/
├─ offices/
├─ territories/
├─ routes/
├─ stockpiles/
├─ formations/
├─ reports/
└─ scenario/
```

发布包可以只带运行所需内容和简化来源清单；完整 Ledger 保留在制作仓库。不要把版权受限的整本资料复制进仓库，只保存合规的书目信息和少量必要摘记。

## 11. 内容校验

自动检查：

- ID 唯一；
- 人物、职位、机构、地区、路线无悬空引用；
- 任职时间与人物生卒无明显矛盾；
- 资源单位存在；
- 路线端点存在；
- Source Ledger 中用于 P0 的关键字段有来源或明确 `DESIGN/OPEN`；
- 内容哈希稳定；
- 许可证必需字段不缺；
- JSON Schema 通过；
- 场景加载后领域不变量通过。

人工审核：

- 来源真的支持该断言，而不只是提到相关主题；
- 时间与地区范围正确；
- 游戏化简化已向团队/玩家诚实说明；
- 人物没有被单一道德标签扁平化；
- 数字的单位和口径可解释。

## 12. MVP 研究问题清单

只研究直接服务“宁远急饷”的问题：

- 选定 1629 具体开局日期及关键历史局势；
- 北京、通州、山海关、宁远、锦州、登莱之间的路线和角色；
- 相关钱粮、仓储、运输和文书的合理抽象；
- 4–6 名关键人物在该时点的身份、关系和职责；
- 能支持海陆方案差异的史实条件；
- 袭粮、天气、道路容量的可用证据范围；
- 哪些细节无法可靠获取，需要明确游戏化。

全国税制、完整科举、所有将领生平和百年技术史不属于这一批。

## 13. 内容完成标准

一项历史内容只有在以下条件全部满足时才能标“生产就绪”：

- 进入当前纵切范围；
- ID、Schema、引用和单位通过；
- 每个关键事实有可核对来源或明确设计标签；
- 冲突与不确定性没有被隐藏；
- 规则映射与简化写清；
- 自动场景加载和不变量通过；
- 玩法测试证明该细节带来可理解的选择；
- 许可证/资产来源清楚；
- 修改后更新 `content_hash` 和存档兼容策略。
