# 小白术语表

> 读到英文名词时先查这里。每个词先给人话，再说明在本项目中的严格含义。

## A–Z

### ABAC（基于属性的权限）

不只看“你是什么职位”，还看地区、金额、对象和时间。例如户部尚书可以调粮，但只限辽东相关仓、最多 8000 石、到某日失效。

### Actor（持久角色身份）

像一个永远有身份证和个人档案的人，需要时才被唤醒处理事情。不是永远运行的线程，也不等于一次 LLM 对话。

### Adapter（适配器）

像插头转换头。核心只知道“我要保存”或“我要请求模型”，适配器把它翻成 SQLite 或某家模型 API 的具体调用。

### ADR（架构决策记录）

一张简短的“为什么这样选”记录，包含背景、决定、代价和何时重评，防止团队反复摇摆。

### Agent（角色代理）

替某个角色作决定的机制组合，包括身份、认知、规则 AI、记忆以及按需模型。Agent 只提出 Intent，不拥有世界。

### API

两个程序/模块约定的说话方式。不是一定走网络；进程内 C# 接口也是一种 API。

### Character / Person（人物）

产品文档统一说“人物”。技术上 `Person` 是有稳定 ID、资料和状态的数据对象；`Agent` 是替人物做决定的机制；`Actor` 强调这个身份会长期存在。三者不是三个不同的人。

### GDD（游戏设计文档）

说明玩家做什么、规则怎样反馈、为何形成选择的文档。它不等于技术架构，也不等于故事背景百科。

### Append-only Journal（只追加日志）

像不能涂改的流水账，新记录只能加在后面。本项目分为 `InputJournal`（世界收到的可重放输入）和 `EventJournal`（提交后发生的事实收据），不等于所有状态都只能靠日志重建。

### Capability（能力/权限种类）

一个角色被允许申请哪类动作，例如 `logistics.authorize_shipment`。它不代表资源一定足够，也不代表动作自动成功。

### Cohort（群体）

把许多相似的人作为一个统计群体模拟，例如“宁远某营 3000 名欠饷军士”，避免为每个人建立复杂对象。

### Command（命令）

“请世界执行这件事”的正式请求。还要经过版本、权限、资源和规则检查，并不代表已完成。

### Commit（提交）

一组状态和事件正式成为历史的原子瞬间。要么全部成功，要么全部不发生。

### Composition Root（装配入口）

程序启动时把 Simulation、SQLite、Agent 和 UI 等对象连接起来的唯一地方。像总管安排各部门，但不亲自办业务。

### Context Compiler（上下文编译器）

从角色可知的信息中挑选与当前任务最相关的一小包，给规则 AI/模型。它防止模型看到完整世界或几十万字无关历史。

### DecisionPacket（决策包）

人物作一次重要判断所需的结构化材料：任务、身份、已知情报、权限、期限和允许的 Intent，不是整个存档。

### DECIDED_BY_ADR / DESIGN

`DECIDED_BY_ADR` 表示原稿没有唯一答案，本项目用架构决策记录选了一条路；`DESIGN` 表示为了玩法/测试暂设的内容。两者都不能冒充“史实已证明”或“原作者最终定案”。

### Deterministic（确定性）

同样的初始状态、命令、内容版本和随机种子会得到同样结果，与电脑速度、帧率和运行次数无关。

### Domain（领域）

游戏世界本身的名词和规则，例如人物、机构、库存、运输与权限，不包含 Godot 控件和 SQL。

### Domain Event（领域事件）

“已经正式发生了什么”的不可变收据，例如 `ShipmentArrived`。请求、计划和模型说法不是事件。

### DTO（数据传输对象）

只用于在模块间传递数据的简单包裹，不拥有业务规则，通常创建后不改。

### Entity（实体）

有稳定身份和生命周期的东西，例如某个人、某批粮队。即使名字或状态变化，ID 仍是同一个。

### Event Sourcing（事件溯源）

把事件日志作为重建状态的主要来源。本项目 V1 不采用严格全量 Event Sourcing，而使用 Current State + Journal + Snapshot。

### GameTime（游戏时间）

世界中的日期和时刻，例如 1629-03-17 06:00。它不是电脑当前时间，也不是渲染帧数。

### Hash（哈希）

把完整规范状态计算成固定长度的“指纹”。相同世界应有相同指纹，用于重放和存档校验。

### Headless（无界面运行）

不启动 Godot 画面，只在命令行运行世界。这样能快速测试十年模拟、重放和规则。

### Hexagonal Architecture（六边形/端口适配架构）

核心通过少量“端口”表达需要，SQLite、模型和 UI 在外围适配。这里只采用轻量边界，不照搬复杂模板。

### Idempotency（幂等）

同一个命令因网络/点击重发多次，也只执行一次；后续重复请求得到原来的结果。

### IngressSequence（输入序号）

玩家点击、模型返回等外部消息被 Simulation 正式接纳时，由单写者分配的连续号码。它像收件编号，固定真实游玩的输入顺序，Replay 不依赖线程运气。

### InputJournal / EventJournal

InputJournal 是“要求世界处理了什么”的输入账；EventJournal 是“提交后实际发生了什么”的收据账。恢复重放用前者，后者用于对照结果和审计。

### Intent（意图）

“这个角色想做什么”的结构化提议。它仍要经过权限和世界规则，不是事实。

### Invariant（不变量）

世界无论怎样变化都必须成立的铁律，例如库存不为负、预约量不超过库存、兵员和装备不能凭空出现。

### LLM（大语言模型）

能理解/生成语言和开放式计划的概率模型。本项目只把它用作重要人物的可选大脑，不用它结算世界。

### Modular Monolith（模块化单体）

玩家只启动一个程序，内部仍有清楚模块边界。没有微服务网络开销，但也不把所有代码混在一起。

### MVP（最小可行/可玩版本）

不是“最少几个界面”，而是最小但完整的一段玩家体验。本项目是“宁远急饷”从下令到运粮、反馈和存档的闭环。

### Narrative（叙事）

把已经提交的事实表达成人能读的奏报、军报或对白。叙事不能创造事实。

### ORM

把数据库表映射成程序对象的工具。首版不使用重型 ORM，只需轻量 SQLite 访问，以免隐藏事务边界。

### P0 / P1 / P2（优先级）

`P0` 是没有它就无法完成当前 MVP 的内容；`P1` 是 MVP 好玩后再增强；`P2` 是方向保留但当前明确不做。P0 不是“最重要的愿望清单”，每项都必须有当前验收。

### Perception Snapshot（感知快照）

为某个角色整理的“他在某时刻能够知道什么”的只读包，与全知 WorldState 不同。

### Port（端口）

核心声明需要的接口，例如 `ICommitStore`。适配器再提供 SQLite 或内存实现。

### RBAC（基于角色/职位的权限）

因担任某职位获得基础能力。它还会结合 ABAC 的范围和限额。

### ReadModel（只读模型）

专门给一个界面或读者整理的数据，例如地图上的可见粮队。它可以重建，不能写回世界。

### Replay（重放）

从一个已知快照按原顺序重新输入命令/已接受 Intent，检查是否得到同样事件与哈希。不会重新问模型。

### Repository

一种数据访问抽象。本项目禁止万能 `IRepository<T>`；只为真实需要定义业务含义清楚的存储端口。

### Scheduler（调度器）

按游戏时间保管“将来何时处理什么”的队列，例如三天后粮队抵达、月初结算军饷。

### Schema（结构规范）

规定 JSON、命令、事件或数据库有哪些字段、类型和版本，防止大家用同一个词表达不同数据。

### Simulation（模拟器）

真正推动世界时间、执行规则、计算结果和提交事实的部分。它是唯一权威写者。

### Single Writer（单写者）

只有一个逻辑执行者能修改世界。UI、AI 和后台存档只能发请求或读取快照，防止并发写炸数据。

### Snapshot（快照）

某个世界版本的完整冻结照片，用于快速加载和故障回退。写完后必须真实加载验证，才能设为当前快照。

### Soak（长跑测试）

让游戏在无界面或自动操作下连续运行很长游戏时间，观察内存、性能、规则漂移和存档问题。MVP 先跑许多次 90 日场景和一年合成长跑，不一开始追求十年。

### State Machine（状态机）

规定对象允许从哪个状态走到哪个状态，例如粮队从 Planned → InTransit → Arrived，不能从 Arrived 回到 Planned。

### Stock–Flow（存量—流量）

存量是当前有多少，流量是一段时间进出多少。国库/仓库是存量，税收/消耗/运输是流量。

### Structured Intent（结构化意图）

模型/规则 AI 按固定 Schema 输出的行动提议，包含类型和参数，而不是靠一段自然语言猜它想做什么。

### Transaction（事务）

一组数据库变化全成功或全失败。例如扣来源粮、增加在途粮、建粮队和写日志必须属于同一次事务。

### Utility AI（效用 AI）

给候选行动按目标、性格、关系、风险和成本打分，选择最高者。适合大量普通人物和模型回退。

### Value Object（值对象）

没有独立身份，只看内容的概念，例如 `Money(5000, silver)`、`GameTime`、`Quantity`。通常不可变。

### Vertical Slice（垂直切片）

从 UI 到规则、状态、存档全部打通的一小段游戏。像竖切一小块蛋糕，虽小但每层都吃得到。

### WAL（Write-Ahead Log）

SQLite 的预写日志模式。修改先追加到 WAL，允许读者和写者并行，但仍只有一个写者；活数据库不能只复制主文件丢下 WAL。

### WorldDelta（世界变化草案）

规则算出的尚未生效变更集合。通过所有检查和数据库事务后才成为世界事实。

### WorldState（世界状态）

当前已提交世界的唯一权威内存表示。UI 卡片、AI 上下文、数据库缓存都不能各自拥有另一份可写真相。

### WorldVersion（世界版本）

每次正式提交后递增的编号。命令用它说明自己基于哪个世界，防止按过期信息透支资源。

### YAGNI

“你现在还不需要它”。没有当前需求和验收，就不为将来的可能性提前写框架、扩展点和空接口。

## 常见易混淆对照

| 容易混淆 | 正确区别 |
| --- | --- |
| Agent vs LLM | Agent 是人物决策机制；LLM 只是可选的一种决策工具 |
| Command vs Event | Command 是请求；Event 是已提交事实 |
| Intent vs Command | Intent 是角色提议；Command 是正式执行请求 |
| Event vs 随机事件卡 | Domain Event 是事实收据；事件卡是内容表现，不可偷偷改状态 |
| WorldState vs SQLite | 两者表示同一已提交版本；SQLite 是持久化，不是另一套业务真相 |
| World Truth vs Belief | 前者是真实世界；后者是某个人相信的版本 |
| Pause vs Turn | 暂停是停止实时游戏时钟；不是等待玩家结束一个季度回合 |
| Render Time vs GameTime | 前者让画面流畅；后者决定历史何时发生 |
| Snapshot vs Save 按钮 | Snapshot 是经验证的完整世界版本；按钮只是触发保存流程 |
| 代码少 vs 复杂度低 | 少行可能隐藏风险；复杂度低还包含正确、可测、可维护 |
| 模块 vs 微服务 | 模块是职责边界；不要求独立进程和网络 |
| 继承 vs 组合 | 人不会继承成“户部尚书”；人 + 任职 + 权限组合出当前角色 |
