# 需求追踪矩阵

## 1. 为什么要有这张表

它把“原始策划说了什么”“我们怎么裁决”“哪份设计解释”“以后用什么证明”连在一起，防止需求在几万行讨论中丢失。

状态：

- `BASELINE`：当前设计基线；
- `DECIDED_BY_ADR`：原稿存在多个候选，本项目通过 ADR 作出的本地裁决；
- `DESIGN`：为玩法/测试暂设的设计值，不是史实或原稿定案；
- `SUPERSEDED`：被原文后期明确修正；
- `CLARIFIED`：保留核心思想，但澄清术语或边界；
- `DEFERRED`：方向保留但不进 MVP；
- `OUT_OF_SCOPE`：当前没有开发承诺，不等同于“迟早会做”；
- `SOURCE-NOTE`：只证明原稿出现过这一线索，不证明它是正式方案；
- `OPEN`：仍需专项设计/史料/试玩。

## 6. 原始文档冲突处理规则

原始文件是 16,691 行多轮对话与研究合并稿，不是单一规格。采用：

1. 明确写“修正、正式采用”的后期决定优先；
2. 原稿仍有多个候选时，不假装存在最终答案；用 `DECIDED_BY_ADR` 记录本地取舍和重评条件；
3. 个人可完成的垂直切片优先于商业全量系统；
4. 安全、确定性、事务和可测试性优先；
5. 世界机制研究作为概念库，不自动变成类清单；
6. 早期联网/云/分布式设计标为当前范围外，不暗示未来承诺；
7. 历史引用必须在生产内容前重新验证，聊天内部引用标记不能直接使用。

## 8. 维护这张矩阵

- 新需求先分配 ID；
- 每个代码任务和测试引用至少一个 ID；
- 需求被修改时保留旧行，标 `SUPERSEDED` 并链接新 ID；
- 没有验收证据的实现状态最多写“已有原型”；
- 每个里程碑结束更新“当前代码覆盖矩阵”；
- 重大历史/玩法假设在 Source Ledger 或 ADR 中补证据，不把本文行号当历史学证据。
