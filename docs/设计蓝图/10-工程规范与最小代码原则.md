# 工程规范与“最小代码”原则

## 1. 先纠正一个危险误解

用户要求“能实现功能的最小代码数量”，正确目标是：

> **使用实现、证明和维护该功能所需的最少总复杂度。**

不是：

- 把十个业务步骤挤成一行；
- 去掉事务、校验和测试以减少行数；
- 所有逻辑塞进一个 `GameManager`；
- 用难懂的技巧赢“代码高尔夫”；
- 只数生产代码、不数修 Bug 和迁移成本。

代码行数是观察信号，不是目标函数。一个 40 行、边界清楚且可测试的规则，可能比 5 行按钮回调更“少”。

## 2. 本项目的复杂度预算

每个功能最多按需要支付以下复杂度：

```text
业务规则本身
+ 一个清楚的命令入口
+ 必要的权限/前置条件
+ 一次原子提交
+ 一个玩家可读结果
+ 能证明正确的测试
```

默认不支付：

```text
微服务
消息中间件
通用工作流平台
每类一个接口
Factory/Builder/Handler/Dispatcher 全套
为了未来可能出现的扩展点
```

## 3. 十五条编码纪律

1. 优先用 .NET/Godot 标准库；引入依赖要说明少掉了什么代码和风险。
2. 一个事实只有一个可写来源；汇总值从事实派生。
3. 所有写入经 Command/Intent → Simulation，不给 UI/Agent 旁路。
4. 领域规则与 Godot、SQLite、HTTP、模型 SDK 分离。
5. 第一个用例先写清楚的具体实现；第二/第三个同因变化出现后再抽象。
6. 只有跨层、多实现或 I/O 测试替身需要时才建接口。
7. 使用组合，不建角色/机构大继承树。
8. 使用强类型 ID、单位和记录，不传任意字符串字典。
9. 预期业务失败用结构化 `Result/Error`，不滥用异常。
10. 内容差异放 JSON；世界机制才写 C#。
11. 不创建万能 `Manager`、`ServiceLocator` 或 `Utils` 垃圾桶。
12. 不为每个操作机械建立 Handler/Factory/Builder。
13. 重复两段很小、变化原因不同的代码，比错误抽象更便宜。
14. 每个变更必须能在无 Godot/无 LLM 的路径验证核心规则。
15. 删除未使用代码和抽象；版本控制就是恢复手段，不留注释掉的墓地。

## 4. 何时抽象、封装、对象化

### 4.1 抽象

抽象是“把真正相同、会一起变化的概念命名”。建立前至少满足一项：

- 出现两个以上真实实现，调用方确实不应知道差异；
- 多处代码因同一个业务原因一起变化；
- 是必须隔离的外部边界；
- 不抽象会破坏状态所有权或测试。

不要因为两段代码长得像就抽象；先问它们是否因同一原因变化。

### 4.2 封装

封装是“外面只能通过合法入口改变状态”。例如库存不公开 `Quantity` setter，而提供预约、释放、转移等规则动作。

好的封装：

```text
库存模块拥有 Quantity/Reserved
外界提交 TransferResource Command
模块返回 WorldDelta 或明确失败
```

这里的 `WorldDelta` 是 Simulation 内部少量**强类型变化记录**的统称，不是通用补丁框架。禁止为了省几行代码建立反射式字段路径、JSON Patch 或 `Dictionary<string, object>`；规则应返回像 `StockTransferChange` 这样编译器能检查的具体记录，再由提交层组合。

坏的封装：

```text
public set; 但大家约定不要乱改
```

### 4.3 对象化

有身份、生命周期、引用或不变量才建实体；只有一组无身份参数就用值对象/record；只是一条算法就用函数/规则类。

## 5. 接口判断表

| 情况 | 是否建接口 |
| --- | --- |
| Application 需要 SQLite/内存两种存储 | 是，跨层且有实现差异 |
| Utility AI 与外部模型都能产出决策 | 是 |
| 一个 20 行纯规则类只有一个实现 | 通常否 |
| 每个领域实体都配 `ICharacter` | 否 |
| 为测试替换真实时间/模型/I/O | 是 |
| “以后也许会换算法” | 否，等需求出现 |
| Godot Presenter 调用 Application 查询 | 可用明确端口，不建万能 Repository |

## 6. 文件和类的大小不是硬指标

以下是代码审查信号，不是机械上限：

- 一个文件包含多个不相关变化原因；
- 一个类同时认识 Godot、SQL、领域规则和模型；
- 方法必须滚动多屏且无法用业务步骤概括；
- 构造函数依赖十几个服务；
- 为理解一次资源转移要跳十几个一行文件；
- 一个模块只有 DTO，规则散落在别处；
- 一个 `switch` 持续增长但每种类型有独立复杂规则。

该拆则拆，该留在一起则留在一起。目标是最少认知跳转，不是最小文件。

## 7. 一个功能的最小纵向结构

以“创建粮食运输”为例，合理最小集合可能是：

```text
CreateShipmentCommand（请求数据）
ShipmentRule / LogisticsService（业务计算，可先是一个具体类）
Shipment（有生命周期的实体）
ShipmentCreated/Departed（提交事实）
2–5 个核心测试
```

不需要：

```text
CreateShipmentCommandFactory
CreateShipmentCommandBuilder
CreateShipmentCommandValidatorInterface
CreateShipmentCommandValidator
CreateShipmentCommandDispatcher
CreateShipmentCommandHandlerFactory
ShipmentRepositoryFactory
```

入口格式校验可以和命令入口放一起；业务资源/权限校验放领域规则；提交由已有 Commit Store 处理。

## 8. 禁止的捷径

以下看似代码少，实际会制造屎山：

### UI 直接改世界

```csharp
// 禁止示意
world.Grain -= 5000;
world.NingyuanGrain += 5000;
```

它跳过权限、在途、容量、时间、损耗、事务和审计。

### AI 文本决定事实

```text
如果回答包含“已完成”，把项目设为完成
```

模型语言不可作为提交协议。

### 多处保存汇总

```text
Facility.Capacity 可写
+ Country.TotalCapacity 可写
```

两份迟早不同步。

### 万能字典

```text
Dictionary<string, object> ChangeGameData(...)
```

它隐藏单位、权限和合法组合，编译器无法帮助。

### 捕获异常后继续

```text
try { commit } catch { log; continue simulation; }
```

提交状态未知时继续推进会扩大损坏。

## 9. 允许的务实选择

- 模块内部可直接调用另一个模块的只读接口，不强制所有东西走消息总线；
- V1 可使用一个小 `switch` 分派少量命令，类型和复杂度增长后再拆；
- 数据量小且逻辑清楚时，线性扫描比提前建索引更好；
- 第一版可以有内存适配器，但不能把它宣称为可靠存档；
- 重复一小段简单映射可以接受，避免制造全局通用 Mapper；
- 测试可以先用无第三方包的可执行冒烟程序，但规则扩大后应迁移到标准测试框架；
- 性能优化只根据 Profile/基准结果，保留清楚的基线实现作对照。

## 10. 错误设计

### 10.1 错误不是字符串日志

结构化错误至少有：

```text
code
human_message
相关对象 ID
retryable
建议补救（可选）
causal_command_id
```

建议错误类别：

| 类别 | 示例 | 处理 |
| --- | --- | --- |
| 输入 | 数量单位缺失 | 请求修正，不入队 |
| 版本 | 基于旧世界 | 重校验或拒绝 |
| 权限 | 超辖区/限额 | 拒绝并解释 |
| 资源 | 可用粮不足 | 拒绝/部分方案由新命令明确提出 |
| 业务状态 | 粮队已出发不能直接取消 | 给合法替代动作 |
| 外围可降级 | 模型超时 | Utility AI 回退 |
| 基础设施 | SQLite 写失败 | 停止发布新世界 |
| 内核缺陷 | 不变量失败 | 立即停止推进并诊断 |

不要自动“部分成功”，除非命令契约明确允许并让玩家/Actor事前授权。

## 11. 测试纪律

测试不是为了覆盖率数字，而是证明风险边界。

### 每个规则功能至少测试

- 一个正常成功；
- 一个关键前置条件失败；
- 一个边界值；
- 一个幂等/重复输入（写操作）；
- 相关资源不变量；
- 结果事件与状态一致。

### 每个跨模块用例至少测试

- 状态、Input/Event Journal、Outcome、Commit 一起成功；
- 中途故障时一起回滚；
- ReadModel 只反映已提交状态；
- 重放得到相同哈希。

### 每个 AI 用例至少测试

- 无模型回退；
- 非法输出；
- 越权；
- 过期；
- 模型声称完成不改变世界。

## 12. 代码审查十问

1. 谁拥有这份状态？
2. 是否出现第二个可写真相？
3. 这段代码是否越过技术层或业务模块边界？
4. 把 Godot、SQLite 或 LLM 换掉，领域规则还能运行吗？
5. 执行到一半崩溃会不会半成功？
6. 单位、ID 和失败是否是强类型/结构化的？
7. 是否可在不启动 Godot 的测试中证明？
8. 新抽象解决了哪个已经出现的问题？
9. 能否删除一个类/接口而保持同样清楚和安全？
10. 玩家能否从结果解释理解发生了什么？

其中第 1–5 项有一项答不上来，先不合并。

## 13. 依赖引入清单

引入 NuGet、Godot 插件或外部服务前写短记录：

```text
要解决的当前问题：
不用依赖需要写/维护什么：
依赖带来的代码减少：
许可证：
更新与安全风险：
是否进入核心确定性路径：
能否离线/替换：
删除方案：
```

如果只是节省十几行且引入复杂运行时，不值得。

## 14. 性能纪律

- 先用垂直切片数据做基准；
- 不每小时遍历所有人物/人口；
- 不每帧查询 SQLite；
- 不每次 UI 刷新重建整个世界 JSON；
- 不用 LLM 处理可公式化批量任务；
- 不先并行化单写规则；先减少计算频率和对象数量；
- 不为性能牺牲确定性；
- 优化前后保留相同输入/哈希测试。

## 15. 文档和代码同步

- 改产品原则：先更新 01；
- 改层或依赖：更新 04/ADR；
- 改模块职责：更新 05；
- 改对象所有权：更新 06；
- 改命令/事件/存档格式：更新 06/08 和追踪矩阵；
- 实现只覆盖设计的一部分时，文档标“已有原型”，不能写“已完成”；
- 注释解释“为什么”，代码本身表达“做什么”。

## 16. Definition of Done

一个功能只有同时满足以下条件才完成：

- 范围和非目标明确；
- 通过正确的命令入口；
- 权限、前置条件和失败行为明确；
- 状态唯一且事务完整；
- 有已提交事件和玩家可读反馈；
- 无 Godot/无 LLM 的核心测试通过；
- 构建无警告（最终应启用 warnings-as-errors 或基线治理）；
- 没有新增未使用抽象和依赖；
- 文档、Schema、迁移和测试同步；
- 在真实 UI/CLI 路径完成一次端到端验收。
