# ADR-005：采用 Current State + Input/Event Journal + Verified Snapshot

状态：Accepted  
日期：2026-08-13

## 背景

项目既需要快速加载/查询，也需要审计、重放和损坏恢复。严格全量 Event Sourcing 会要求所有历史和迁移都能从第一条事件重建，对首版个人项目过重；只保存传统快照又无法解释因果和安全恢复。

## 决定

SQLite 保存可直接查询的 Current State。每个会改变权威世界的 Commit 同一事务写 Current State、对应外部 `InputJournal`（若有）或 `ActionOutcome`、`EventJournal`、Outcome 和 Commit；Scheduled Action 不重复写成外部输入。空小时直接跳过，但权威 GameTime 每次实际推进到下一动作、暂停点或 `AdvanceTo` 目标时，即使没有其他 Delta，也必须提交时间状态。周期生成不可变 Snapshot，真实加载和校验通过后才切换当前指针。

正常加载直接读取健康的 Current State；恢复/确定性 Replay 使用“READY Snapshot + 后续 InputJournal”，并把 EventJournal/Commit hash 当作预期输出校验。活动数据库可以有 WAL 配套文件，但玩家导出的 `.mingsave` 使用 SQLite Backup API 生成单一自洽文件。

原研究稿偏向内存推演后周期持久化；“每个世界变化 Commit 先同步落盘再发布内存”是本 ADR 为故障一致性作出的本地强化裁决，不冒充原文结论。

## 原因

- 查询和加载简单；
- 正式变化有审计链；
- 重放与 Bug 复现可行；
- 快照损坏可退回上一 READY；
- 代码和迁移复杂度低于严格 Event Sourcing。

## 代价

- 必须确保 Current State、输入/事件日志、Outcome 与 Commit 在同一事务；
- Schema 迁移要同时考虑状态、事件和快照；
- 不是所有派生历史查询都能只靠事件免费获得。
- 同步持久化可能增加 I/O；先用“无变化不提交、动作独立小事务”控制，再以测量决定是否需要耐久批次。

## 被否决方案

- 仅序列化一个 SaveGame：缺少审计、事务和回退；
- 严格 Event Sourcing：V1 不需要从创世事件重建所有状态；
- 多数据库/对象存储：单机没有必要，跨库事务更难。

## 何时重新评估

以下任一条件有可重复数据时才重评：Current State 无法满足真实时态查询/分支需求；或同步 Commit 在目标硬件成为可感知瓶颈。若改为短耐久批次，新 ADR 必须写明最大可丢游戏进度、崩溃语义和恢复测试；不能悄悄退回“内存成功、数据库稍后再说”。

## 验证

- SQLite 故障注入全有或全无；
- Input/Event Journal 连续性；
- 快照先验证后切换；
- 损坏回退；
- 同一 Replay 得到同一哈希。
