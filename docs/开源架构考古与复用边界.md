# 开源架构考古与复用边界

## 结论先说

这次没有把四个外部项目的源码或资源复制进 MingSim。它们被放在独立的参考目录中，用来确认架构选择和接口边界：

- Open Historia：重点借鉴“地图几何与可序列化文档状态分离”，以后可以把它作为独立地图编辑器候选。
- OpenVic / OpenVic-Simulation：重点借鉴“Godot 展示层与独立仿真库分离”，以及确定性调度、命令缓冲和状态校验的思想。
- Sparta：重点借鉴“纯逻辑 CampaignState + 严格 Loader + seed/orders 回放”的小型可读实现。

MingSim 继续保持自己的 C# Simulation Microkernel，不把 React/OpenLayers、C++ ECS 或 GDScript 运行时硬塞进核心工程。

## 1. Open Historia：地图工具链

### 观察到的结构

Open Historia 的地图编辑器文档明确把数据分成两部分：

1. React 文档状态：名称、类型、城市、颜色、旗帜、标签和元数据，轻量且可序列化；
2. OpenLayers `VectorSource`：承载大量区域几何，只有保存/导出时才序列化回文档。

它还把地图导出分成两个层级：

- Tier 1：保留既有 GADM 区域编号，只输出所有权覆盖和静态颜色等内容；
- Tier 2：发生新画、切分、合并或改形时，另外输出 `regions.geojson`，让游戏直接使用自定义几何。

这套分层解决了一个很实际的问题：绝大多数“换谁占领”不需要重新保存数千个多边形，而真正改地图形状时又不会把变化伪装成普通所有权变化。

### 对 MingSim 的采用

- 已采用：MingSim 新增 `Ming.Domain.Map.MapDefinition`，只保存静态省份编号、名称和有向邻接关系；动态占领、驻军和人物位置仍在 `WorldState` 及其领域对象中。
- 已采用：地图拓扑进入规范化快照哈希，几何坐标不进入仿真哈希。
- 以后可采用：单独建立 `Tools/Ming.MapAuthoring`，输入/输出 JSON + GeoJSON；Godot 只加载导出的表现层数据。

### 明确不直接复制

- 不把 React/OpenLayers 组件复制到 Godot 项目；技术栈和运行时边界不同。
- 不把 Open Historia 的默认历史地图、图片、PMTiles 或 GeoJSON 当作 MingSim 自带资产。代码的 MIT 许可不自动替代地图数据的来源和历史考证。
- 不把地图编辑器的文档状态直接当作 `WorldState`；编辑器输出必须先经过 MingSim 的内容校验器。

## 2. OpenVic：Godot 与仿真边界

### 观察到的结构

OpenVic 主仓库要求 Godot 4.7、CMake、Ninja 和 Python，并把核心模拟作为 `OpenVic-Simulation` 子模块。Godot 侧通过 GDExtension 类和单例把省份位置、地图标记、贴图/投影等数据转换成引擎可用的类型；地图视图用信号向 UI 报告 hover、click、zoom 等交互。

### 对 MingSim 的采用

- 已采用：`Ming.Godot` 只做展示和输入转换，规则结算继续在 `Ming.Simulation`。
- 已采用：当前场景使用图片和标签作为表现数据，不把世界状态写进 Godot Node。
- 以后可采用：为 `Ming.Application` 做明确的查询/命令 DTO，再由 Godot 适配器订阅已提交的 `WorldState` 与 `DomainEvent`。

### 明确不直接复制

- 不为了“像 OpenVic”而把 C++/GDExtension 引入第一版 C# 项目。
- 不把 OpenVic 的 Godot 4.7 工程文件直接覆盖当前已验证的 Godot 4.6 预览工程。
- 不让 UI 单例拥有第二份可写世界状态；所有写入必须经过 Application → Simulation。

## 3. OpenVic-Simulation：确定性仿真参考

### 观察到的结构

OpenVic-Simulation 的 ECS 文档把确定性写成了可测试的契约，而不是口号：

- 使用整数/定点数，避免浮点结果跨编译器或平台漂移；
- 系统通过访问声明形成确定性 DAG；
- 回合/ tick 内的结构性变化进入 `CommandBuffer`，在阶段屏障统一应用；
- worker 数量改变时，归并顺序仍固定；
- 世界有完整状态 checksum，另有 identity snapshot 处理存档后的实体编号稳定性；
- 数据加载先解析、校验，再写入注册表/定义管理器。

### 对 MingSim 的采用

- 已有对应物：`SimulationKernel` 的冻结工作区、`InvariantChecker`、`DeterministicRandom`、`InMemorySnapshotStore` 和规范化 `StateHasher`。
- 本次增强：`StateHasher` 现在会按省份编号排序，把地图编号、名称和邻接列表纳入哈希。
- 设计约束：如果未来出现跨子系统的批量结构变化，应新增“命令收集 → 阶段提交”的边界，而不是允许某个 Agent 或 Godot 直接改 `WorldState`。

### 明确不直接复制

- 当前规模还不需要复制 C++ ECS、线程池和 GDExtension ABI；先保持可读的 C# 对象模型。
- 不把“有 checksum”误认为“已经有完整 replay”。目前 MingSim 仍缺少可重放的命令日志格式，这列入下一阶段。

## 4. Sparta：小型状态、内容加载和回放

### 观察到的结构

Sparta 的 `CampaignState.gd` 明确声明为无 Scene/Node 依赖的纯逻辑，并由单元测试直接调用。`CampaignLoader.gd` 把文件读取和已解析字典的 `parse_map()` 分开，检查空阵营、重复编号、未知邻接、自环、多边形和外交引用等错误。`CampaignMap.gd` 负责点击、绘制、HUD 和把输入转成状态方法调用。

它的 Replay 使用固定 seed 和按 tick 记录的 orders；另外区分仿真轨道和纯展示轨道（相机、指针、键盘），并在加载时检查格式版本和物理 tick 率。这个区分很适合 MingSim：玩家命令要进入可验证日志，镜头动画不应改变世界结果。

### 对 MingSim 的采用

- 已采用：场景 JSON 与运行时领域对象分离，`ScenarioLoader` 负责反序列化，`MapDefinition` 负责拓扑验证。
- 已采用：地图中允许显式有向邻接，不在加载时偷偷补边；这让山口、渡口等规则不会被“好心修复”成另一张地图。
- 以后可采用：`WorldIntent` / `DomainEvent` 之外新增 `TurnCommandJournal`，保存 seed、基准回合、命令顺序、结果哈希和版本信息。

### 明确不直接复制

- 不把 Godot 的 `RandomNumberGenerator` 作为 MingSim 的规则随机源；C# 规则继续使用显式输入派生的确定性随机。
- 不把 Sparta 的战术战斗模型直接混入明代政务模拟；只吸收状态边界和回放验证方法。

## 许可证与资产边界

- 本次参考的四个仓库及 Open Historia 地图编辑器声明为 MIT；如果未来复制具体代码，必须保留对应版权和许可证文本，并记录文件来源。
- 本次没有复制 Open Historia 的历史地图数据、图片、PMTiles 或 GeoJSON。
- OpenVic 的主仓库和 Simulation 子模块需要按其固定子模块提交配套构建；不能把两个不同 HEAD 混成一个“看似完整”的依赖。
- OpenRA、Unciv、Microsoft Agent Framework、MCP C# SDK 和 LiteLLM 目前只作为目标文件里的后续参考方向，本次没有把它们加入 MingSim，也没有声称已经完成相应源码审计。

## 下一阶段顺序

1. 为 `TurnCommandJournal` 定义最小 JSON 格式：版本、世界编号、起始状态哈希、seed、意图顺序、事件哈希、最终状态哈希。
2. 写一个无 Godot 的 replay smoke test：同一剧本 + 同一命令日志必须得到同一最终哈希；输入顺序或版本不匹配要明确失败。
3. 再做独立地图 authoring 工具，先导出 `MapDefinition` 拓扑和单独 GeoJSON，不把编辑器依赖引入运行时。
4. 最后让 Godot 通过 Application 查询和命令端口消费真实 `WorldState`，而不是直接读取或修改领域对象。
